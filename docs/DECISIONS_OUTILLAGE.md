# Décisions tranchées — OUTILLAGE

> **Comment la sandbox agit sur la machine de Mike** : les trois canaux, le
> pilotage du serveur, la livraison git, les superviseurs. Chaque piste, son
> verdict, pour ne rien re-proposer.
>
> **Pourquoi ce fichier existe** (20/08, choix de Mike). `eval/DECISIONS.md`
> débordait pour la deuxième fois en deux jours. L'archive PAR STATUT avait été
> rejetée le 19/08, et à raison : elle coupait un même domaine en deux selon
> l'âge, donc il fallait relire les deux fichiers pour ne rien re-proposer.
> Le découpage par DOMAINE n'a pas ce défaut — le réflexe est lui-même par
> domaine. Qui travaille la recherche n'a jamais besoin de savoir pourquoi
> `taskkill` a échoué ; qui touche aux canaux n'a que faire du gazetteer.
> Précédent : `eval/METHODE.md`, sorti le 16/08.
>
> Le détail des travaux vit dans **git** ; la méthode dans `eval/METHODE.md` ;
> ce qui concerne la PHOTOTHÈQUE elle-même dans `eval/DECISIONS.md`.

## Pilotage du serveur

| Idée / piste | Verdict | Raison |
|---|---|---|
| Route HTTP, ou serveur qui se relance seul | **REJETÉ** (19/08) | Il ne peut garantir que son port est libéré, et s'il rate son réveil la sandbox reste dehors. |
| `arret` coupe aussi le superviseur | **REJETÉ** (19/08) | Un arrêt sans retour est un piège, Mike absent : `arret` met le superviseur en ATTENTE. Illisible → `marche`. |
| Libérer le port PUIS les préparatifs lents | **CORRIGÉ** (19/08) | 40 s de `pip` entre le kill et le démarrage : un orphelin reprenait le port. Le lent passe AVANT ; port tenu après 10 essais → on ne lance RIEN. |
| `taskkill` par TITRE DE FENÊTRE retire l'ancien superviseur | **FAUX** (20/08) | Il ne retrouve pas fiablement les fenêtres console : il n'a RIEN tué. L'ancien superviseur a survécu, a pris pour un plantage le kill par PID de son serveur, et en a relancé un second — **deux fenêtres « MediaLibrary - Serveur »**, le verrou de port passé pourtant. Remplacé par une GÉNÉRATION : le bat 0 écrit un jeton neuf, chaque superviseur le relit à chaque tour et se retire s'il a changé. Un titre se devine, un fichier se lit. |

| **Un JOURNAL du serveur, pas seulement une console** | **ADOPTÉ** (23/08, demande de Mike, `journal_serveur.py`) | Tout ce que `server.py` raconte allait dans une fenêtre `cmd.exe` — chez Mike, et nulle part ailleurs. Une erreur affichée là avait expliqué un défaut en une ligne, mais il avait fallu qu'un humain la lise et la recopie ; et un thread qui meurt la nuit ne laissait rien du tout. Un MIROIR sur `stdout`/`stderr` : la console garde exactement ce qu'elle avait, `_journal_serveur.log` garde la même chose DATÉE, lisible à distance sans le serveur. Il ajoute ce qu'un `print` ne donne pas : une bannière de démarrage (« depuis que ce serveur tourne » devient une question qui se répond), les exceptions non rattrapées du fil principal **et des threads** — le cas qui n'apparaissait NULLE PART, un worker meurt, sa file se remplit, et le serveur a l'air vivant — et les plantages durs des libs natives via `faulthandler`, dans un fichier à part. Rejeté en chemin : une route HTTP pour lire le journal (un journal qui exige le serveur vivant est inutile le jour où le serveur meurt) et `logging` (un réglage global qui change le comportement de toutes les libs importées, pour un besoin qui tient en un miroir). Borné à 4 Mo + une archive, et toute écriture ratée est avalée : un disque plein ne doit pas tuer la photothèque. **15 vérifications.** Au passage, une console `cp1252` qui refuse un caractère ne fait plus tomber ce qui l'entoure — le défaut du 22/08 — et le journal, lui, garde le vrai texte. |
## Livraison git

| Idée / piste | Verdict | Raison |
|---|---|---|
| **Livrer dans git depuis la sandbox** | **ADOPTÉ, OBSERVÉ** (19/08) | `git` lancé depuis la VM laisse un `.git/index.lock` qu'elle ne sait pas supprimer (elle écrit, elle n'efface pas) : jamais un principe, une impossibilité. Un agent WINDOWS lance le vrai git. Premier acte observé : il s'est commité lui-même (`a43f9d0`, 10 fichiers), push et fast-forward de main compris. |
| L'agent est un bouton déporté | **REJETÉ** (19/08) | Il est la **porte** : refus tant que le serveur ne tourne pas le code visé, qu'un test est rouge, qu'un `.bat` n'est pas ASCII ou que le lint crie. D'où l'ordre **inversé**. |
| **`commit` = branche + push** | **CORRIGÉ, OBSERVÉ** (20/08, choix de Mike) | `CLAUDE.md` l'annonçait, le code s'arrêtait au commit LOCAL — vérifié dans `.git`, pas dans le rapport de l'agent : `refs/remotes/origin/feat/…` n'existait pas. Une traite autonome ne vivait donc que sur le disque de Mike, le scénario même du chantier 12 (« PC mort lundi »). Les deux modes poussent désormais ; `main` reste intacte, car c'est elle que la convention protège, pas l'absence de copie. Le banc tournait « sans distant » : il VALIDAIT le défaut — il tourne maintenant contre un dépôt bare local. |
| `force=` lève tous les contrôles | **REJETÉ** (19/08) | Il lève les NÉGOCIABLES — serveur à jour, tests, `.bat`, lint — et sa raison part dans le journal. Jamais le verrou `.git/*.lock`, jamais `main`, jamais un binaire (`photos.db` fait 290 Mo), jamais un `checkout` vers une branche EXISTANTE, qui réécrirait `server.py` sous le serveur qui tourne. Six tests vérifient exactement ce qu'il n'ouvre pas. Premier usage réel le 20/08 : budget de doc dépassé, arbitrage rendu à Mike. |
| Loger l'agent dans le serveur | **REJETÉ** (19/08) | Le serveur est l'OBJET du commit ; un git qui bloque bloquerait une requête ; et un serveur du LAN qui lance git est une surface qu'on ne veut pas. |

## Les trois canaux

| Idée / piste | Verdict | Raison |
|---|---|---|
| Une fenêtre d'agent minimisée | **REJETÉ** (19/08) | Elle s'est fermée sans que personne le voie : une fenêtre morte-née était indiscernable d'une fenêtre en écoute, et rien ne se livrait sans que rien ne le dise. Fenêtre VISIBLE, `_agent_*_vu.txt` touché à chaque tour, commande `ping` inerte, contrôle du bat 0 après 6 s. |
| **Un troisième canal : lancer un BANC sous Windows** | **ADOPTÉ, OBSERVÉ** (20/08) | La sandbox n'atteint pas le LAN (`X-Proxy-Error: blocked-by-allowlist`) : un banc qui interroge le serveur — c'est lui qui détient SigLIP — ne peut pas tourner chez elle. Livré NON TOURNÉ, il a fallu le clavier de Mike, et sa sortie a RÉFUTÉ une conclusion tirée de deux échantillons. `banc_agent` ne lance QUE les familles qui MESURENT (`mesure_ verifier_ diagnostic_ comptes_ inventaire_ test_ eval_`), sans shell (`subprocess.run` reçoit une liste : `&&` n'est pas filtré, il est sans effet), sans chemin, sans `force=`. Observé : `verifier_bat.py` rendu en 0,1 s accents intacts, `purger_corbeille.py` refusé pour sa famille, `mesure_faits_vue.py --base photos.db` refusé par le banc lui-même. |
| Loger les bancs chez l'agent git | **REJETÉ** (20/08) | Un banc de dix minutes bloquerait le canal de livraison pendant tout ce temps — c'est-à-dire exactement au moment où l'on veut livrer ce qu'on vient de mesurer. Troisième fenêtre, à contrecœur : elle coûte à Mike, le blocage coûterait plus. |
| **Fabriquer la COPIE de la base restait un geste de Mike** | **ADOPTÉ, OBSERVÉ** (21/08) | Tous les bancs exigent `--base copie.db` et refusent `photos.db` — mais personne ne fabriquait la copie. Le jour où elle n'est plus à la racine, le canal qui existe pour mesurer SANS le clavier de Mike se rebloque sur ce clavier : c'est arrivé le 21/08. `mesure_copie_base.py` la fait par l'API `backup` de SQLite, source ouverte en `mode=ro` — un descripteur qui ne PEUT pas écrire. Un `copy` du seul `.db` était faux, et le banc le chiffre : **5,4 Mo** vivaient dans le WAL, hors du fichier — une base ouvrable et périmée d'autant, le pire des trois états. Observé par le canal : 276,5 Mo en **0,9 s**, `quick_check` **ok**, 43 065 `tags`. La copie est DATÉE dans la sortie : sans son instant, on croit mesurer aujourd'hui ce qui date d'avant-hier. |
| Trois canaux, trois lecteurs de fichier | **CORRIGÉ** (20/08) | La lecture tolérante (BOM, CRLF, LF nu) et l'écriture atomique en CRLF explicite étaient recopiées DEUX fois à l'identique ; une troisième copie et la règle cessait d'exister. `canal.py` les porte ; chaque agent garde son VOCABULAIRE et sa porte. `lire_ligne` ne met rien en minuscules — un canal transporte un chemin, et `Copie.db` n'est pas `copie.db`. |

## Ouvrir la photothèque à un agent (MCP)

| Idée / piste | Verdict | Raison |
|---|---|---|
| **Un serveur MCP local, LECTURE SEULE** | **ADOPTÉ, OBSERVÉ** (23/08, `mcp_serveur.py`, point 13) | JSON-RPC 2.0 sur stdio, stdlib pure — ni npm, ni SDK, ni framework (règle 3). Six outils : `ml_chercher`, `ml_semblables`, `ml_meme_jour`, `ml_sujets`, `ml_photos_de`, `ml_etat`. **41 vérifications**, plus **15** pour le banc, et **13 mutations posées une à une dans le module : 13 vues** — un module neuf n'a pas d'« ancien code » à rougir, la mutation est ce qui en tient lieu. Observé contre le serveur VIVANT (`mesure_mcp.py`, 12 étapes, 0 rouge) : poignée de main en 0,09 s, 351 personnes, `espece:chat` filtré. |
| Lire `photos.db` plutôt que l'API | **REJETÉ** (23/08) | Le serveur est l'écrivain unique (règle 4), et un second lecteur du fichier vivant lit un état que le WAL n'a pas encore rangé. L'API dit ce que le serveur SAIT, à l'instant où il le sait. Effet de bord décisif : n'appelant **aucune route neuve**, le module est livrable un jour où `server.py` a changé sous un serveur qui n'a pas redémarré — le seul point de la feuille dont la preuve ne dépendait pas du redémarrage. |
| La lecture seule par convention | **REJETÉ** (23/08) | Une note « ne pas écrire » n'arrête personne. `ClientLecture` n'a **aucune** méthode d'écriture et refuse tout chemin absent de `CHEMINS_PERMIS` : ajouter un outil qui écrit demande de changer le CLIENT, pas d'ajouter une ligne. Un test garde la liste contre `/api/assign`, `/api/people/rename`, `/api/maint/run`. |
| Passer les réponses de l'API telles quelles | **REJETÉ, ET CHIFFRÉ** (23/08) | `/api/people/photos` rend **4 013 486 octets** pour Florine. L'outil coupe à 20 photos, jette ce qui ne s'adresse qu'à une interface (`crop_url`, `gurl`, `folder`, `i`, `sim`) et rend **5 775 octets** : **695× moins, 0,14 % gardé**. Sans ça, un seul appel remplit le contexte de l'agent qui l'a fait. |
| **Deux plafonds MUETS, trouvés en OBSERVANT et non en lisant** | **CORRIGÉ** (23/08) | Le premier était le mien : en demandant `n=5` à `/api/search`, l'outil annonçait « 5 trouvées » pour `espece:chat`, un axe qui en porte 2 386 — il comptait ce qu'il avait DEMANDÉ. Le second est dans la route : sans `limit`, `/api/people/photos` rend exactement **2 000** photos pour Florine, qui en porte **5 909**, et ne le dit nulle part. Parade unique : on demande à chaque route SON maximum, et `total_est_un_plancher` distingue un compte d'un plafond atteint. C'est la leçon de la page de recherche (ROADMAP 14a), re-payée deux fois le même jour dans un module écrit pour l'appliquer. |
| **`faits` : une ROUTE, pas un second assemblage** | **ADOPTÉ** (23/08, `/api/faits`) | La ligne de faits n'était calculée que dans `_serve_browse`, pour la page : rien d'autre — ni banc, ni MCP — ne pouvait la lire. La refaire côté MCP aurait été un SECOND assemblage, exactement ce que `faits_vue` existe pour empêcher (« un deuxième assemblage, même fidèle, finit par diverger »). La route rend un LOT (`?key=` répétable, 200 au plus) parce que le contexte (`_faits_ctx`) coûte cher et se bâtit UNE fois — un test compte les appels, sans quoi le lot coûterait ce qu'il prétend éviter. **Trois états qui ne se confondent pas** : les faits, `null` pour une photo connue qui ne porte rien, la clé citée dans `inconnues` quand l'index l'ignore — confondre les deux derniers ferait lire « cette photo ne porte rien » là où il faut lire « je ne connais pas cette photo ». **16 vérifications, 8 mutations posées, 8 vues.** Seule route NEUVE du lot : elle attend le redémarrage, et le banc MCP le DIT au lieu de le taire. |
| **Le jeton `b64:` — porter un nom humain jusqu'au banc** | **ADOPTÉ, OBSERVÉ** (23/08, `banc_agent.py`) | Le canal refusait tout argument hors `[A-Za-z0-9_.:/=-]`. Le garde-fou ne visait pas les noms — il les a attrapés au passage : **168 des 352 noms, 6 119 photos** étaient hors de portée de `verifier_xmp_personnes.py`, le seul instrument qui prouve la règle 2 dans les FICHIERS. Trouvé le jour où Mike a nommé le groupe de « Stéphane Plouvin » et où la preuve de son geste s'est révélée inlançable. Le jeton transporte la valeur en base64url — que `ARG_OK` admettait DÉJÀ : la porte n'est pas desserrée d'un caractère, les trois barrières jugent la forme écrite, et la valeur n'est reconstituée qu'APRÈS elles, pour la LISTE de `subprocess.run`. Le nom du BANC n'est jamais décodé (la famille se juge sur l'écrit). Jeton vide, hors alphabet, non-UTF-8 ou porteur d'un caractère de contrôle : refus NOMMÉ. **11 vérifications neuves, 8 ROUGES sur l'ancien code** (3 sont des invariants, verts des deux côtés — c'est leur rôle), et l'en-tête de `_banc_sortie.txt` DIT ce qui a réellement tourné. |
| Élargir `ARG_OK` aux accents, ou accepter les quotes | **REJETÉ** (23/08) | Les deux marchaient. Élargir l'alphabet laissait l'ESPACE dehors — donc « Stéphane Plouvin » aussi, et la moitié du problème avec. Accepter les quotes demandait un découpage à échappement dans `decouper`, c'est-à-dire la première brique d'un shell dans un agent dont la barrière 1 est de n'en être pas un. Le jeton ne touche ni à l'alphabet, ni au découpage. |
| **Éditer un `.bat` pendant qu'il tourne tue sa fenêtre** | **CONSTATÉ, PAYÉ** (23/08) | Une ligne d'aide ajoutée à `superviseur_banc.bat` — ASCII pur, `verifier_bat.py` vert — pendant que `cmd.exe` l'exécutait : `_agent_banc_vu.txt` a cessé de battre dans la minute, la fenêtre des Bancs est morte en silence, celle de Git a continué. C'est la règle 1 sous une face qu'elle ne nommait pas : ce n'est pas le CARACTÈRE qui décale, c'est l'ÉDITION elle-même. Le contrôle avant livraison ne voit pas ce défaut-là — il lit le fichier, pas la fenêtre. Porté dans `CLAUDE.md` : éditer, puis faire ROUVRIR la fenêtre, et vérifier le battement. |
| **Le contrôle 5 jugeait sur le NOM ; il lit maintenant le GRAPHE** | **ADOPTÉ, OBSERVÉ** (23/08, `graphe_du_serveur`) | `py_a_observer` n'excluait que `test_` et `mesure_`, donc il réclamait à `mcp_serveur.py`, `banc_agent.py`, `git_agent.py` lui-même et aux familles `appliquer_`/`verifier_` la preuve qu'un serveur les fait tourner — une preuve qui **n'existe pas** : le serveur ne les importe jamais. C'est ce qui obligeait à écrire `force=`, et **un contrôle qu'on contourne par habitude ne contrôle plus rien** : forcer pour un faux positif entraîne à forcer tout court. La règle lit désormais `server.py` et tout ce qu'il importe, imports PARESSEUX compris (règle 3 : les imports lourds vivent dans les fonctions — un graphe qui ne lit que le premier étage les manquerait tous). Rien n'est importé pour de vrai : `ast` lit le source, et un nom sans fichier dans le projet est un nom externe. **Mesuré sur le dépôt : 29 modules dedans, 134 dehors.** Un import DYNAMIQUE dont le nom n'est pas écrit en clair est un **TROU** : le contrôle le NOMME et retombe sur la vieille règle de nom, plus large — le doute penche du côté qui redemande une preuve. Un seul trou est admis, daté et justifié (`TROUS_ADMIS`) : `semantic.cmd_diagnostic` fait `__import__(nom)` sur `open_clip`/`transformers`, deux bibliothèques externes. Une exception écrite vaut mieux qu'une heuristique qui devine. **17 vérifications neuves, 13 rouges sur l'ancien code, 45/45 vertes sous Windows dans le dossier du projet** — dont quatre qui mesurent le VRAI dépôt, un banc sur un projet inventé ne mesurant que l'imagination de qui l'a écrit. |
